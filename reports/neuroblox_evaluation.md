## K1. Многотемповое интегрирование

**Приоритет: ключевой**

**Что найдено.**
Neuroblox.jl собирает все блоки в единый граф (`system_from_graph`), из которого
ModelingToolkit.jl генерирует одну `ODESystem` / `SDESystem`. Эта система решается одним
вызовом `solve(prob, solver)` с одним адаптивным шагом. В документации и туториалах
используются `Tsit5()` (explicit, non-stiff) и `Vern7()` (explicit, high-order), для
стохастики — `RKMil()`.

Механизма раздельного интегрирования подсистем с разными характерными временами **нет**.
Обмен переменными на границах тактов не реализован. Понятие `timescale` в блоке
отсутствует.

Однако Neuroblox стоит на экосистеме DifferentialEquations.jl, которая поддерживает:
- stiff solvers (`Rodas5`, `TRBDF2`, `KenCarp4` и др.);
- IMEX через `SplitODEProblem` (жёсткая часть implicit, остальное explicit);
- multirate infinitesimal (MRI) через ARKODE.

Теоретически можно вручную переформулировать систему как `SplitODEProblem`, но
Neuroblox не делает этого автоматически и не предоставляет API для пометки блоков
как fast/slow.

**Вердикт: нет.** Наши требования включают многотемповое интегрирование с разрывом
4–5 порядков между подсистемами. Поддержка stiff solvers есть на уровне
Julia-экосистемы, но не на уровне Neuroblox.

**Источники:**
- [Neuroblox course — neural mass models](https://neuroblox.github.io/course/pages/neuron_mass/)
- [DifferentialEquations.jl — Split ODE Solvers](https://docs.sciml.ai/DiffEqDocs/stable/solvers/split_ode_solve/)
- [JuliaCon 2025 talk](https://pretalx.com/juliacon-2025/talk/BC7V3E/)

## K2. Эпизодическая динамика со сбросом

**Приоритет: ключевой**

**Что найдено.**
Neuroblox поддерживает discrete_events на уровне отдельного блока — например, сброс
мембранного потенциала при спайке: `(V > θ) => [u ~ u + d, V ~ V_reset]`. Также есть
`connection_callbacks` для межблочных событий (spike-driven).

Для обучения есть `run_experiment!` с `N_trials` и `trial_dur`, где пластичность
применяется между прогонами симуляции. Однако это не встроенная пробовая структура
в самом движке: это внешний цикл, который перезапускает `solve()` между пробами.

Понятия «проба» как единицы, разделения состояния на эпизодическое (сбрасывается)
и непрерывное (сохраняется), триггера пробы — **нет** в контракте блока. Блоки
определяют только `system` и `namespace`; пробовая логика реализуется снаружи.

В нашей архитектуре DDM — эпизодический модуль, работающий внутри непрерывного
композита (возбуждение, настроение не останавливаются между пробами). Neuroblox
не имеет механизма для такого гибридного режима.

**Вердикт: нет.** Discrete events для спайков есть. Пробовая структура с
селективным сбросом подмножества модулей — нет. Реализуемо через callbacks
DifferentialEquations.jl, но Neuroblox не предоставляет абстракции для этого.

**Источники:**
- [Neuroblox course — Blox and Connections](https://neuroblox.github.io/course/pages/blox_connections/)
- [Neuroblox course — Learning and Plasticity](https://neuroblox.github.io/course/pages/learning/)

## K3. Контракт модуля

**Приоритет: важный**

**Что найдено.**
Блок Neuroblox — Julia struct с двумя обязательными полями: `system` (ModelingToolkit
ODESystem) и `namespace`. Переменные состояния и параметры определяются внутри
конструктора через `@variables` и `@parameters`. Метаданные `[output=true]` и
`[input=true]` помечают входы/выходы.

Покрытие нашего контракта:

| Элемент контракта | Покрытие Neuroblox |
|---|---|
| `state` — имена, размерности | Да, через `@variables` |
| `params` — диапазоны | Нет. Параметры задаются значениями по умолчанию, диапазонов нет |
| `params` — exposed/internal | Нет. Все параметры одного статуса |
| `inputs` / `outputs` | Да, через метаданные `[input=true]`, `[output=true]` |
| `timescale` | Нет |
| `drift(x, θ, u)` | Частично. Уравнения задаются в конструкторе, но не как вызываемая функция |
| `diffusion(x, θ)` | Частично. Шум добавляется через параметр σ, но не как отдельная функция |
| `validation` | Нет |

**Вердикт: частично.** Базовая структура (state, inputs, outputs, equations) есть.
Диапазоны параметров, разделение exposed/internal, timescale, validation — нет.

**Источники:**
- [Neuroblox course — Blox and Connections](https://neuroblox.github.io/course/pages/blox_connections/)
- [Neuroblox docs landing](https://neuroblox.github.io/NeurobloxDocsHost/dev/)

## K4. Произвольные модули

**Приоритет: важный**

**Что найдено.**
Создание пользовательского блока документировано и работает. Нужно определить Julia
struct `<: AbstractBlox` (или подтип вроде `Neuron`, `NeuralMass`), задать произвольные
уравнения через `@variables`, `@parameters` и массив `eqs`, обернуть в
`System(eqs, t, sts, params; ...)` — и блок подключается к графу.

Пример из документации:

```julia
struct IzhNeuron <: Neuron
    system
    namespace
    function IzhNeuron(; name, namespace=nothing, a=0.02, b=0.2, ...)
        sts = @variables V(t)=-65 [output=true] u(t)=-13 jcn [input=true]
        params = @parameters a=a b=b V_reset=V_reset d=d θ=threshold
        eqs = [D(V) ~ 0.04*V^2 + 5*V + 140 - u + jcn + 5,
               D(u) ~ a*(b*V - u)]
        event = (V > θ) => [u ~ u + d, V ~ V_reset]
        sys = System(eqs, t, sts, params; name=name, discrete_events=event)
        new(sys, namespace)
    end
end
```

Также можно определить пользовательские `connection_equations` и `connection_callbacks`
через multiple dispatch. Дисперсия определяется через SDE-формулировку
(StochasticDiffEq.jl) при необходимости.

**Вердикт: да.** Произвольные drift/diffusion реализуемы. Система расширяема.

**Источники:**
- [Neuroblox course — Blox and Connections](https://neuroblox.github.io/course/pages/blox_connections/)

## K5. Устойчивость композиции

**Приоритет: важный**

**Что найдено.**
Встроенных инструментов для анализа устойчивости (линеаризация, спектр якобиана,
поиск критической силы связи) **нет** ни в Neuroblox, ни в GraphDynamics.jl.

ModelingToolkit.jl может вычислить символьный якобиан системы, что даёт основу
для линеаризации. В экосистеме Julia есть BifurcationKit.jl — зрелый пакет для
анализа бифуркаций и устойчивости. Но Neuroblox не интегрирован с ним.

Для нашего правила 19 (устойчивость перед композицией) потребуется:
- Извлечь символьную систему из Neuroblox-графа
- Найти стационарную точку (нелинейная задача)
- Вычислить якобиан и его спектр
- Параметрически пройти по силе связи

Всё это делается вручную, но на Julia-экосистеме это технически достижимо.

**Вердикт: нет** (встроенного). Инструменты экосистемы позволяют построить анализ
рядом с Neuroblox, но интеграция отсутствует.

**Источники:**
- [BifurcationKit.jl](https://bifurcationkit.github.io/BifurcationKitDocs.jl/dev/library/)
- [GraphDynamics.jl](https://github.com/Neuroblox/GraphDynamics.jl)

## K6. Связь как модуляция параметра

**Приоритет: важный**

**Что найдено.**
Связи в Neuroblox реализуются через **аддитивное суммирование в переменную `jcn`**
(junction current). Выход блока-источника (`[output=true]`) взвешивается и добавляется
к входной переменной блока-приёмника (`[input=true]`). Пример:

```
destination.jcn ~ weight * source.G * (destination.V - source.E_syn)
```

Это классическое суммирование переменных состояния, а **не** модуляция параметра.
Связь `θ_i ← h(x_j)` — когда выход одного модуля изменяет **параметр** (не вход)
другого — не поддерживается стандартным механизмом.

В ModelingToolkit.jl параметры по определению константы. Чтобы сделать параметр
зависимым от другой переменной, нужно переформулировать его как вспомогательную
переменную (observed / algebraic variable). Это технически возможно, но:
- меняет семантику «параметр = крутилка пользователя»;
- не поддержано Neuroblox API;
- требует переформулировки уравнений при каждой связи.

**Вердикт: нет.** Стандартный механизм Neuroblox — суммирование состояний.
Наш проект требует связи как модуляции параметра; это не покрыто текущим API.

**Источники:**
- [Neuroblox course — Blox and Connections](https://neuroblox.github.io/course/pages/blox_connections/)
- [GraphDynamics.jl](https://github.com/Neuroblox/GraphDynamics.jl)

## K7. Стоимость Julia

**Приоритет: практический**

**Что найдено.**

*Язык.* Автор работает на Python/Jupyter. Neuroblox — Julia. Варианты:
1. Полный переход на Julia. JuliaCon 2025 workshop использует Jupyter с IJulia —
   формат знакомый, но язык другой.
2. juliacall (PythonCall.jl) — вызов Julia из Python. Зрелый, поддерживает
   многопоточность, zero-copy для массивов. Но: startup time Julia (~10–30 с
   при первой компиляции), два рантайма, отладка через границу языков сложна.
3. PyJulia — старый интерфейс, development stalled, не рекомендуется.

*Лицензия.* Neuroblox распространяется по EULA (не open source):
- Академическое использование бесплатно; модификация и перераспределение
  исходного кода не разрешены.
- Коммерческое использование требует отдельного соглашения.
- Код нельзя «rent, sell, time-share, lease, sublicense, transfer, copy,
  disclose, display, or otherwise make available».
- Юрисдикция: Massachusetts, обязательный арбитраж в Бостоне.

Наш проект требует воспроизводимости и права на модификацию кода;
лицензия Neuroblox этого не допускает.

*Экосистема.* DifferentialEquations.jl, ModelingToolkit.jl, BifurcationKit.jl —
всё MIT-лицензировано, зрело, активно развивается. Основная ценность — в экосистеме,
не в Neuroblox-обёртке.

**Вердикт:** Переход на Julia (или двуязычная архитектура), лицензия EULA.
Julia-экосистема (DiffEq, MTK, BifurcationKit — MIT) доступна без Neuroblox.

**Источники:**
- [Neuroblox LICENSE.md](https://github.com/Neuroblox/Neuroblox.jl/blob/main/LICENSE.md)
- [PythonCall/JuliaCall](https://juliapy.github.io/PythonCall.jl/stable/)
- [JuliaCon 2025 Workshop](https://github.com/Neuroblox/JuliaCon2025WS)

## K8. Образец без зависимости

**Приоритет: практический**

**Что найдено.**
Архитектурные решения Neuroblox, которые стоит заимствовать:

1. **Граф блоков.** `MetaDiGraph` с блоками-вершинами и связями-рёбрами →
   `system_from_graph` → единая система. Паттерн «граф → составная ODE» ортогонален
   языку, реализуем на Python (networkx + собственный компилятор).

2. **Типизация блоков для dispatch.** Иерархия `AbstractBlox → Neuron → ExciNeuron`
   позволяет определять дефолтные связи через dispatch. В Python аналог —
   `@singledispatch` / множественный dispatch через `multipledispatch` или паттерн
   Visitor.

3. **Символьная генерация уравнений.** ModelingToolkit позволяет упрощать и
   оптимизировать уравнения до численного решения. В Python аналог — SymPy
   (с меньшей интеграцией в численные солверы).

4. **Метаданные на переменных** (`[output=true]`, `[input=true]`). В Python —
   dataclass поля с аннотациями или attrs.

Наши требования, не покрытые Neuroblox:
- `timescale` у блока
- диапазоны и exposed/internal у параметров
- пробовая структура (episodic vs continuous state)
- связь как модуляция параметра
- встроенная проверка устойчивости

Эти элементы требуют собственной реализации независимо от выбора платформы.

**Вердикт: да.** Архитектурный паттерн (граф → система) полезен как образец.
Но всё, специфичное для нашего проекта (K1, K2, K6, K5), не покрыто Neuroblox
и потребует собственной реализации.

**Источники:**
- [Neuroblox course — CS Circuit](https://neuroblox.github.io/course/pages/CS_circuit/)
- [GraphDynamics.jl](https://github.com/Neuroblox/GraphDynamics.jl)

## Варианты решения (для автора)

### Вариант A: Neuroblox как основа

Взять Neuroblox, надстроить недостающее: многотемповое интегрирование, пробовую
структуру, параметрическую связь, анализ устойчивости.

*За:*
- Готовая библиотека нейронных моделей (HH, LIF, Izhikevich, WilsonCowan, Jansen-Rit).
- Производительность Julia (×100 vs TVB заявлено).
- Активное сообщество (JuliaCon, курсы, публикации в Nature Communications).

*Против:*
- Оба ключевых требования (K1, K2) не покрыты → существенная доработка.
- Лицензия EULA: модификация кода не разрешена. Доработки возможны только
  поверх существующего API.
- Смена языка (Julia) или двуязычная архитектура.
- Стандартный механизм связи — суммирование состояний; наша архитектура
  требует модуляции параметров, что потребует переформулировки уравнений.

### Вариант B: Своё ядро на Python, заимствуя паттерны

Реализовать собственный движок: контракт модуля, граф связей, многотемповой
интегратор, пробовая структура — на Python.

*За:*
- Полный контроль над контрактом модуля (все поля из CLAUDE.md, включая
  timescale, exposed/internal, episodic/continuous).
- Связь как модуляция параметра — нативно, не через обход API.
- Пробовая структура в ядре, а не снаружи.
- Многотемповое интегрирование по дизайну: раздельные интеграторы, обмен
  на границах, усреднение.
- Python — рабочий язык автора.
- Никакой лицензионной зависимости.

*Против:*
- Всё с нуля. Интеграторы (Euler-Maruyama минимум, желательно выше порядком),
  символьная генерация — только если нужна (SymPy).
- Производительность Python ниже Julia. Для масштабов проекта (4 модуля, не
  тысячи нейронов) это не критично, но если позже масштабировать — может стать.
- Нет готовой библиотеки моделей (но нам и не нужна: модели строятся по
  formalisms_report, а не берутся из каталога).

### Вариант C: Своё ядро на Python + Julia-экосистема для тяжёлых вычислений

Python-ядро для контракта, графа, пробовой структуры, анализа устойчивости.
Для тяжёлого интегрирования — вызов DifferentialEquations.jl через juliacall,
минуя Neuroblox.

*За:*
- Контроль над архитектурой (как B).
- Доступ к stiff/IMEX солверам и BifurcationKit из Julia.
- Лицензионная чистота (DiffEq, MTK, BifurcationKit — MIT).

*Против:*
- Два рантайма, startup overhead Julia, сложность отладки.
- Избыточно для текущего масштаба (4 модуля).
- Усложняет воспроизводимость: установка Julia + пакеты.

## Рекомендация (техническая, не научная — научное решение за автором)

**Рекомендация: Вариант B.** Своё ядро на Python.

Обоснование:

1. Оба ключевых критерия (K1, K2) не покрыты Neuroblox. Их реализация поверх
   существующего API потребует больше работы, чем реализация с нуля в ядре,
   спроектированном под эти требования.

2. Связь как модуляция параметра (K6) — фундаментальное архитектурное решение
   проекта. Neuroblox использует суммирование состояний. Реализация модуляции
   параметра потребует переформулировки уравнений при каждой связи, что
   не поддержано API и не допускается лицензией на уровне исходного кода.

3. Масштаб проекта: 4 модуля, каждый — 2–5 переменных состояния. Это не
   тысячи нейронов. Euler-Maruyama с правильным √dt, корректно написанный
   на numpy, достаточен. Если позже упрёмся в производительность — переход
   на Вариант C (juliacall для солверов) возможен без переписывания
   архитектурного слоя.

4. Проект требует воспроизводимости и права на модификацию кода. Лицензия
   Neuroblox (EULA) этих прав не предоставляет.

5. Из Neuroblox стоит заимствовать паттерн «граф блоков → составная система»
   (K8 = да). Это архитектурная идея, не код.

Риски варианта B и их митигация:
- Интегратор: Euler-Maruyama минимален. Если нужна схема выше порядком —
  `sdeint` или `torchsde` (MIT), или свой Milstein.
- Символьный якобиан: SymPy или автодифференцирование (JAX). Для 4 модулей
  с ~10 переменными — вычислимо за секунды.
- Масштабируемость: при необходимости (фаза 4+) — juliacall для солверов,
  не меняя ядро.
